# Consolidated site: architecture

## Site structure

The site is package-centric. Adopters install one package at a time, and every package already owns its README, guides, and changelog.

```
/                              landing page
/guide/getting-started         install, import, bundle check
/guide/<topic>                 cross-package topics: choosing a package, tree-shaking, using with agents
/packages/                     grid of all published packages, one line each, current version
/packages/<pkg>/               the package README
/packages/<pkg>/guides/<slug>  from libs/<pkg>/docs/*.md
/packages/<pkg>/api/...        TypeDoc markdown for that package only
/packages/<pkg>/changelog      the package CHANGELOG.md
/releases/                     all releases across packages, newest first
/llms.txt, /llms-full.txt, /llms/<pkg>/*   generated by scripts/agentDocs.ts
```

The top navigation has four items: Guide, Packages, Releases, LLMs, plus GitHub and Discord icons. The sidebar follows the section. Inside a package the sidebar lists Overview, Guides, API, and Changelog. RFCs stay on GitHub.

`<pkg>` is the folder name under `libs/`, for example `cmcd`. The list of packages comes from `scripts/projects.ts`, so unpublished packages such as `mse` do not appear.

## Workspace

A `site/` workspace replaces `docs/`. The package name is `@svta/common-media-library-site` and it is private. The root `package.json` lists `site` in `workspaces` instead of `docs`.

Three new root devDependencies: `vitepress`, `typedoc-plugin-markdown`, and `typedoc-vitepress-theme`. Both plugins require TypeDoc 0.28.x, which the repo already runs. Vue arrives with VitePress and is not a direct dependency.

Hand-written site content is limited to the landing page, `site/guide/*.md`, and `site/adopters.json`. Every package page is generated from `libs/`.

Layout:

```
site/
  .vitepress/config.ts        nav, sidebar, base path, search
  .vitepress/theme/           custom home components
  index.md                    landing page
  guide/                      cross-package guides
  public/                     logo, favicon, 404.html
  adopters.json               hand-maintained adopters list
  typedoc.json                TypeDoc with the markdown plugins
  scripts/prepare.ts          generates every package page, see below
  scripts/*.test.ts           tests for the generators
  packages/                   generated, gitignored
  releases/                   generated, gitignored
  dist/                       build output, gitignored
```

## Build pipeline

`npm run build -w site` runs three steps: `node scripts/prepare.ts`, `vitepress build`, then `node ../scripts/agentDocs.ts --site dist`. `npm run docs` at the root runs the prepare step and the VitePress dev server.

`prepare.ts` does five things in order:

1. **Package pages.** For each package, copy `README.md` to `site/packages/<pkg>/index.md`, `docs/*.md` to `guides/`, and `CHANGELOG.md` to `changelog.md`. Add frontmatter for the title and the sidebar position. Rewrite relative links: `docs/x.md` becomes `./guides/x`, `../other/README.md` becomes `/packages/other/`, `CHANGELOG.md` becomes `./changelog`. Any other link to a repo file becomes a GitHub URL. Links inside fenced code blocks stay unchanged.
2. **API reference.** Run TypeDoc with the two plugins and the packages entry point strategy. Output goes under `site/packages/<pkg>/api/`. The VitePress theme plugin writes `typedoc-sidebar.json`. The VitePress config slices that file per package.
3. **Releases feed.** Parse every `## [x.y.z] - YYYY-MM-DD` heading in every `CHANGELOG.md`. Sort by date, newest first. Write `site/releases/index.md` with one entry per release: package, version, date, and a link to the changelog page. Unreleased sections are skipped.
4. **Package index data.** Write `site/packages/packages.json` with name, description, version, and link for every package. The landing grid and the `/packages/` page read this file.
5. **Redirect stubs.** From the TypeDoc reflection list, write one HTML stub per old URL into `site/public/`: `/enums/X.html`, `/functions/X.html`, `/types/X.html`, `/interfaces/X.html`, `/classes/X.html`, `/variables/X.html`, `/documents/X.html`, and `/modules/X.html`. Each stub has a meta refresh and a canonical link to the new page. GitHub Pages has no server-side redirects, so stubs are the only option.

VitePress fails the build on dead links. This check covers every README and guide in the repo.

## Landing page

The landing page uses the VitePress `home` layout for the hero and three custom Vue components below it.

1. **Hero.** Wordmark, a one-line tagline, one sentence on what CML is, and two buttons: Get started and Browse packages. An install snippet sits beside the text.
2. **Features row.** Four items: spec-accurate, tree-shakeable, typed, zero peer dependencies outside CML.
3. **Package grid.** Reads `packages.json`. A map in the VitePress config assigns each package to a group. Packages inside a group sort alphabetically.
4. **Adopters.** Reads `site/adopters.json`: name, logo, URL, and the packages used. The first version lists only consumers verified in their repositories, dash.js for cmcd at minimum.
5. **Community.** Discord, GitHub Discussions, the SVTA working group, and the contributing guide.
6. **Footer.** "A Streaming Video Technology Alliance project" and the license.

Package groups:

| Group | Packages |
| --- | --- |
| Delivery | abr, cmcd, cmsd, content-steering, request, throughput |
| Containers | cmaf-ham, dash, id3, iso-bmff |
| Captions | 608, cta, webvtt |
| Trust | c2pa, drm |
| Core | error-codes, iso-8601, structured-field-values, utils, xml |

## Branding constraints

The visual design pass happens in phase 3 and must respect these constraints:

- A new SVG wordmark and mark.
- One accent color. Light and dark modes through the VitePress theme variables.
- System font stack, or one self-hosted webfont. No third-party requests.
- No analytics and no tracking scripts.
- The built landing page scores 95 or higher on Lighthouse performance, measured with the Lighthouse CLI against a local server over `site/dist`.

## Deploy

The three workflows that publish today, `docs.yml`, `publish.yml`, and `publish-package.yml`, change two lines each: build `site` instead of `docs`, and publish `./site/dist/`. The peaceiris action and the `gh-pages` branch stay.

The VitePress base path comes from the `SITE_BASE` environment variable. The default is `/`. The workflows set `/common-media-library/` until the domain cutover.

## Domain

SVTA points `cml.svta.org` at `streaming-video-technology-alliance.github.io` as a DNS-only CNAME. This replaces the current 301 to the WordPress page. The repository settings set the custom domain and enforce HTTPS. GitHub then redirects the github.io URL to the custom domain, so old bookmarks keep working. The WordPress page on svta.org links to the new site. Both changes belong to SVTA.

## Previews

Decision on 2026-10-22: preview changes locally with `npm run docs`. GitHub Pages has no native preview deploys. If previews become necessary later, deploy pull request builds to `preview/<pr-number>/` on the `gh-pages` branch with the peaceiris `destination_dir` option. Add a `noindex` tag to preview builds. Delete the folder when the pull request closes.

## Quality gates

- A `site.pr.yml` workflow builds the site, without deploying, on pull requests that touch `site/`, any `README.md`, `libs/*/docs/`, or `libs/*/CHANGELOG.md`.
- `site/scripts/*.test.ts` run under `node --test` and cover link rewriting, changelog parsing, release feed order, and the redirect map.
- A post-build smoke check asserts that these files exist in `site/dist`: one package overview, one API page, one redirect stub, `llms.txt`, and `404.html`.
- The spike in `phases.md` measures build time and the local search index size. If the index exceeds 2 MB, API member pages leave the search index and stay reachable through the sidebar.
