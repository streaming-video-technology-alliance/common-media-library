# Consolidated site: architecture

Amended on 2026-10-22 after the phase 1 spike. The amendments are listed at the end.

## Site structure

The site is package-centric. Adopters install one package at a time, and every package already owns its README, guides, and changelog.

```
/                              landing page
/guide/getting-started         install, import, next steps
/packages/                     every published package, grouped by domain, with version and description
/packages/<pkg>/               the package README
/packages/<pkg>/guides/<slug>  from libs/<pkg>/docs/*.md
/packages/<pkg>/changelog      the package CHANGELOG.md
/api/                          index of the API reference, one link per package
/api/<pkg>/...                 TypeDoc markdown for that package
/releases/                     all releases across packages, newest first
/llms.txt, /llms-full.txt, /llms/<pkg>/*   generated by scripts/agentDocs.ts after PR 557 lands
```

The top navigation has three items: Guide, Packages, Releases, plus GitHub and Discord icons. PR 557 adds a fourth item, LLMs. The sidebar follows the section. Inside a package the sidebar lists Overview, Guides, API, and Changelog. The API pages of a package show the same sidebar, so a reader never leaves the package. RFCs stay on GitHub.

`<pkg>` is the folder name under `libs/`, for example `cmcd`. The list of packages comes from `scripts/projects.ts`, so unpublished packages such as `mse` do not appear.

## Workspace

A `site/` workspace replaces `docs/`. The package name is `@svta/common-media-library-site` and it is private. The root `package.json` lists `site` in `workspaces` instead of `docs`.

Three new root devDependencies, pinned: `vitepress` 1.6.4, `typedoc-plugin-markdown` 4.14.1, and `typedoc-vitepress-theme` 1.1.4. Both plugins require TypeDoc 0.28.x, which the repo already runs. Vue arrives with VitePress and is not a direct dependency.

Hand-written site content is limited to the landing page, `site/guide/*.md`, and `site/adopters.json`. Every package page is generated from `libs/`.

Layout:

```
site/
  package.json
  typedoc.json                TypeDoc with the markdown plugins, extends api-entry.json
  index.md                    landing page
  guide/getting-started.md
  public/favicon.png
  .vitepress/config.ts        nav, sidebar, base path, search
  .vitepress/theme/index.js   default theme plus custom.css
  scripts/
    prepare.ts                generates package pages, packages.json, releases, api-entry.json
    typedocModuleNames.ts     TypeDoc plugin: module name "@svta/cml-cmcd" becomes "cmcd"
    writeRedirects.ts         writes the redirect stubs into dist
    check.ts                  smoke check of dist
    *.ts, *.test.ts           pure helpers and their tests
  api-entry.json              generated, gitignored
  api/                        generated, gitignored
  packages/                   generated, gitignored
  releases/                   generated, gitignored
  dist/                       build output, gitignored
```

## Build pipeline

`npm run build -w site` runs these commands in order:

1. `node scripts/prepare.ts`. For each package in `scripts/projects.ts`: copy `README.md` to `site/packages/<pkg>/index.md` with `docs/<file>.md` links rewritten to `guides/<file>.md`, copy `docs/*.md` to `guides/`, and copy `CHANGELOG.md` to `changelog.md`. Then write `site/packages/packages.json` (folder, name, version, description, group, guides), `site/packages/index.md`, `site/releases/index.md`, and `site/api-entry.json` with the TypeDoc entry points.
2. `typedoc`. Packages strategy over the entry points, markdown output under `site/api/<pkg>/`, and `site/api/typedoc-sidebar.json`. The plugin `typedocModuleNames.ts` renames each module from the package name to the folder name on `Application.EVENT_VALIDATE_PROJECT`. That event fires after link resolution and before URLs are built.
3. `vitepress build`. The config reads `packages.json` and `typedoc-sidebar.json` at config load time with `readFileSync`, never with a static import, so `tsc` does not need the generated files.
4. `node scripts/writeRedirects.ts`. Walks `site/api` and writes one HTML stub per old URL into `site/dist`: `<dir>/_svta_cml-<pkg>.<Symbol>.html` for symbols, `modules/_svta_cml-<pkg>.html` for packages, `documents/_svta_cml-<pkg>.<Title>.html` for guides, plus `modules.html` and `hierarchy.html`. Each stub has a meta refresh and a canonical link. GitHub Pages has no server-side redirects, so stubs are the only option.
5. `node ../scripts/agentDocs.ts --site site/dist`, run from the repo root, once PR 557 has landed.
6. `node scripts/check.ts`. Fails when a required output file is missing or the search index exceeds 2 MB.

`npm run docs` at the root runs steps 1 and 2 and then the VitePress dev server.

The releases feed parses every `## [x.y.z] - YYYY-MM-DD` heading in every `CHANGELOG.md`. It sorts by date and then package name. Each release becomes one table row with a link to the changelog page. Unreleased sections are skipped.

VitePress fails the build on dead links. This check covers every README and guide in the repo.

## Search

Local search with minisearch. API pages contribute only their title and first paragraph to the index. Guides, READMEs, and changelogs are indexed in full. The spike measured 877 KB for 503 full API pages and 35 KB for 178 title-only pages.

## Landing page

Phase 2 ships the VitePress `home` layout with a hero and a features row from frontmatter. Phase 3 adds three custom Vue components below it.

1. **Hero.** Wordmark, a one-line tagline, one sentence on what CML is, and buttons: Get started, Browse packages, GitHub.
2. **Features row.** Four items: spec-accurate, tree-shakeable, typed, peer dependencies only inside CML.
3. **Package grid** (phase 3). Reads `packages.json`. The group map in `site/scripts/groups.ts` assigns each package to a group. Packages inside a group sort alphabetically.
4. **Adopters** (phase 3). Reads `site/adopters.json`: name, logo, URL, and the packages used. The first version lists only consumers verified in their repositories, dash.js for cmcd at minimum.
5. **Community** (phase 3). Discord, GitHub Discussions, the SVTA working group, and the contributing guide.
6. **Footer.** "A Streaming Video Technology Alliance project." and the license.

## Branding constraints

The visual design pass happens in phase 3 and must respect these constraints:

- A new SVG wordmark and mark.
- One accent color. Light and dark modes through the VitePress theme variables.
- System font stack, or one self-hosted webfont. No third-party requests.
- No analytics and no tracking scripts.
- The built landing page scores 95 or higher on Lighthouse performance, measured with the Lighthouse CLI against a local server over `site/dist`.
- A custom 404 page with search and a link to the package index. Phase 2 ships the VitePress default 404 page.

## Deploy

The three workflows that publish today, `docs.yml`, `publish.yml`, and `publish-package.yml`, change two lines each: build `site` instead of `docs`, and publish `./site/dist/`. The peaceiris action and the `gh-pages` branch stay.

The VitePress base path comes from the `SITE_BASE` environment variable. The default is `/`. The workflows set `/common-media-library/` until the domain cutover.

## Domain

SVTA points `cml.svta.org` at `streaming-video-technology-alliance.github.io` as a DNS-only CNAME. This replaces the current 301 to the WordPress page. The repository settings set the custom domain and enforce HTTPS. GitHub then redirects the github.io URL to the custom domain, so old bookmarks keep working. The WordPress page on svta.org links to the new site. Both changes belong to SVTA.

## Previews

Decision on 2026-10-22: preview changes locally with `npm run docs`. GitHub Pages has no native preview deploys. If previews become necessary later, deploy pull request builds to `preview/<pr-number>/` on the `gh-pages` branch with the peaceiris `destination_dir` option. Add a `noindex` tag to preview builds. Delete the folder when the pull request closes.

## Quality gates

- A `site.pr.yml` workflow builds the site, without deploying, on pull requests that touch `site/`, `libs/*/README.md`, `libs/*/docs/`, or `libs/*/CHANGELOG.md`.
- `site/scripts/*.test.ts` run under `node --test` through `npm test -w site`. They cover link rewriting, frontmatter, changelog parsing, release feed order, the package index, the search excerpt, and the redirect map.
- `check.ts` asserts that a fixed list of output files exists and that the search index stays under 2 MB.

## Amendments after the spike

1. The API reference lives at `/api/<pkg>/`, not `/packages/<pkg>/api/`. TypeDoc writes one tree with relative links between packages. Moving the folders would break those links. The package sidebar still lists the API, so the reader sees no difference.
2. Redirect stubs are written after the VitePress build, straight into `site/dist`, because VitePress cleans the output folder.
3. API pages contribute title and first paragraph to the search index instead of leaving the index entirely.
4. Phase 2 ships one guide, getting started. Other cross-package guides are content work for a later pull request.
5. Phase 2 ships the VitePress default 404 page. The custom 404 page moves to phase 3.
6. Unpublished packages are excluded through the generated `api-entry.json`, which `typedoc.json` extends.
